WHAT THIS PROVES
  The session cookie is issued with SameSite=None, so the browser attaches it to
  requests started by other websites. With no CSRF token to check, a malicious page
  can act as a logged-in user.

METHOD: black box — read the Set-Cookie header the server sends

$ curl -i -X POST $BASE/api/v1/user/patient/register -d '{...}'

  Set-Cookie: patientToken=eyJhbGciOiJIUzI1Ni….eyJpZCI6IjZhYjM3OTcyOTAxNjVjZDJhNWIzOTE4YyIsImlhdCI6MTc5MDE0NjkzMCwiZXhwIjoxNzkwMjMzMzMwfQ.HgdvWHk4ggOWXqPuf3clBu6Mq06rYh5cGal9AyOERVY; Path=/; Expires=Thu, 24 Sep 2026 07:02:10 GMT; HttpOnly; Secure; SameSite=None

  SameSite : None   <-- the problem
  HttpOnly : yes (correct, but does not stop CSRF)
  Secure   : yes

$ grep -ril "csrf" backend/src backend/app.js
  (no matches — no CSRF protection exists)
